# 01. Одно SQLite-соединение на JS-рантайм

**Дата:** 2026-09-20
**Автор:** mikhail
**Статус:** Принято
**Связанные решения:** —


## Контекст

Приложение падало с `NullPointerException` внутри `NativeDatabase.execAsync` без осмысленного сообщения. Краш происходил в произвольный момент — через секунды или минуты после того, как отрабатывал headless-хендлер виджета, — поэтому стектрейс указывал на самый длинный вызов (`syncTodoistData`), а не на реальный источник.

Диагностика по исходникам `expo-sqlite`, `expo-modules-core` и `react-native-android-widget` показала use-after-free нативного SQLite-хэндла:

1. `openDatabaseAsync` кэширует нативные соединения по пути к файлу БД. Второй вызов с тем же именем файла не открывает новое соединение, а возвращает тот же нативный объект и увеличивает refcount
2. Регистрация shared-объекта в `expo-modules-core` не проверяет, зарегистрирован ли уже этот нативный объект — она безусловно создаёт новую JS-обёртку с независимым `NativeState`. На один нативный `NativeDatabase` оказывается две независимые JS-обёртки
3. Когда Hermes собирает осиротевшую JS-обёртку сборщиком мусора, срабатывает `sharedObjectDidRelease` → `resetNative()`, который уничтожает нативный объект **для обеих JS-обёрток сразу**, не проверяя refcount. Следующий вызов через любую из обёрток уходит в JNI на уже освобождённый `HybridData` → `NullPointerException`

Два независимых JS-владельца одного и того же файла БД возникали из-за того, что `SQLiteProvider` в UI-дереве приложения и собственный `openDatabaseAsync` в headless-хендлере виджета открывали соединение независимо друг от друга. Баг Android-only: на iOS реестр shared-объектов переиспользует id и native state при повторной регистрации. Это подтверждено независимо — [boardsesh#5410](https://github.com/boardsesh/boardsesh/issues/5410) описывает тот же механизм. Апстрим-issue [expo#28176](https://github.com/expo/expo/issues/28176) заведена ещё на SDK 50 и остаётся неисправленной.

Мьютекс или лок поверх хранилища (например, сериализация вызовов через промис-очередь или AsyncStorage-флаг) не устранил бы проблему: `expo-sqlite` собирается в режиме `SQLITE_THREADSAFE=1` и сама сериализует конкурентный доступ через одно соединение, поэтому гонки данных на уровне SQL нет. Падение вызвано освобождением нативного указателя сборщиком мусора — событием, не синхронизированным с моментом SQL-запроса, — и лок поверх хранилища на него никак не влияет.


## Решение

Инвариант: `openDatabaseAsync` вызывается ровно один раз за жизнь JS-рантайма, `closeAsync` не вызывается никогда, полученный объект держится в module-scope переменной.

Реализовано в `getDatabase()` (`src/features/database/api/getDatabase.ts`) — мемоизированный промис, который открывает соединение, прогоняет миграции и отдаёт готовую БД. Module-scope ссылка держит JS-обёртку живой сильной ссылкой, поэтому сборщик мусора до неё не добирается, и нативный хэндл живёт столько же, сколько рантайм. Поскольку UI-приложение и headless-хендлер виджета делят один JS-рантайм, module-scope singleton — это process-wide singleton.

Доступ к БД из React-дерева идёт через `DatabaseProvider`/`useDatabase()` (`src/shared/model/DatabaseContext.tsx`) — обычный React Context, куда `getDatabase` передаётся пропом из композиционного корня (`src/app/(app)/_layout.tsx`), а не импортируется напрямую: это единственный способ сделать доступ к БД доступным из `entities`-хуков без нарушения направления импортов FSD (`entities` не может импортировать `features`). `SQLiteProvider`/`useSQLiteContext` из `expo-sqlite` выпилены полностью.

Миграции переехали внутрь `getDatabase()` — раньше они выполнялись только при монтировании `(app)`-layout, что означало: `WIDGET_UPDATE` на приложении, ни разу не открытом на переднем плане, падал на `no such table`. Теперь любая точка входа (UI или headless) получает мигрированную БД.

Правило `noRestrictedImports` в `biome.json` запрещает прямой импорт `openDatabaseAsync`, `SQLiteProvider` и `useSQLiteContext` из `expo-sqlite` везде, кроме `getDatabase.ts` — юнит-тестом эту ошибку не поймать (она нативная и зависит от таймингов GC), поэтому линтер — единственный постоянный барьер.

Отвергнутая альтернатива: `openDatabaseAsync(DATABASE_NAME, { useNewConnection: true })` в headless-хендлере — фикс в одну строку, но вводит настоящую многосоединённую конкуренцию (WAL, `busy_timeout`, `BEGIN IMMEDIATE` вместо дефолтного deferred) вместо того, чтобы убрать этот класс проблем целиком.


## Последствия

- Краш `NullPointerException` при повторном открытии/закрытии приложения с виджетами на экране устранён — единственный способ подтвердить это окончательно — ручная проверка на устройстве (10–15 циклов сворачивания/разворачивания), автотестом GC-таймингзависимый баг не воспроизвести
- Headless-путь (виджет) теперь гарантированно получает мигрированную БД, даже если приложение ни разу не открывалось на переднем плане
- Любой новый код, которому нужен доступ к SQLite, обязан идти через `getDatabase()`/`useDatabase()` — прямой `openDatabaseAsync` за пределами `features/database` теперь ошибка линтера, а не молчаливо работающий, но опасный паттерн
- `closeAsync()` для этого соединения не вызывается никогда за всё время жизни приложения — это осознанный компромисс: соединение живёт, пока жив процесс
