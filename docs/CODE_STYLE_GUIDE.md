# Code Style Guide

Руководство по архитектуре и оформлению кода для **Focus Widgets**. Технический контекст проекта — [`SPECIFICATION.md`](SPECIFICATION.md).


## Технологический стек

| Технология | Назначение в проекте |
|---|---|
| **Expo** + **Expo Router** | Скаффолд приложения, файловая маршрутизация (`src/app/`), нативные модули (`expo-sqlite`, `expo-secure-store`) |
| **React Native** | UI-слой приложения и виджетов |
| **react-native-android-widget** | Рендеринг Android-виджетов (**Pin**, **List**) React-компонентами (`FlexWidget`/`ListWidget`) |
| **[Todoist SDK](https://www.npmjs.com/package/@doist/todoist-sdk)** (`@doist/todoist-sdk`) | Типизированный клиент Todoist API |
| **TanStack Query** | Серверное состояние — кэш запросов к Todoist API через Todoist SDK |
| **React Hook Form** + **Zod** | Формы (авторизация, конфигурация виджета) и их валидация |
| **day.js** | Форматирование и сравнение дат (due-даты задач) |
| **expo-sqlite** | Локальное хранение конфигурации фильтров виджетов |
| **expo-secure-store** | Хранение Todoist Access Token |

Перед использованием любого Expo/EAS API — правило из [`AGENTS.md`](../AGENTS.md): проверяй версию SDK в `package.json` и версионированные доки, не отвечай по памяти.


## Архитектура (FSD)

Архитектура — **Feature-Sliced Design** с высоким уровнем декомпозиции на компоненты: одна логическая/визуальная единица — новый компонент. Код стремится к **низкой связанности и высокому зацеплению (low coupling & high cohesion)**.

Слои (сверху вниз — верхний может импортировать только из нижних, никогда наоборот):

| Слой | Алиас | Назначение | Пример в этом проекте |
|---|---|---|---|
| `app` | `@/app` | Инициализация приложения: провайдеры (`QueryClientProvider`, тема), глобальные стили | `QueryClientProvider`, конфигурация `QueryClient` |
| `pages` | `@/pages` | Экраны — композиция виджетов/фич/сущностей под конкретный route. Собственной бизнес-логики почти не содержат | Экран списка **Виджетов**, экран формы **Виджета** |
| `widgets` | `@/widgets` | Крупные самостоятельные блоки UI, собранные из нескольких фич/сущностей | Список **Виджетов** с превью и FAB, форма конфигурации query-строки |
| `features` | `@/features` | Одно пользовательское действие с бизнес-ценностью | Вход по токену, создание/удаление **Виджета**, размещение виджета на экране Android |
| `entities` | `@/entities` | Бизнес-сущности домена — их UI-представление и модель | **Задача** (Task), **Виджет** (Widget), **Проект** (Project) |
| `shared` | `@/shared` | Переиспользуемый код без привязки к бизнес-логике: UI-кит, утилиты, типы | `shared/lib/date.ts` (day.js) |

Слой заводится только тогда, когда для него есть код, — пустые директории впрок не создаются. Устаревший в FSD 2.0 слой `processes` не используется.

Внутри слайса — сегменты `ui/` (компоненты), `model/` (состояние, бизнес-логика, Zod-схемы) и `api/` (обёртки над источниками данных и хуки TanStack Query поверх них).

- **Todoist API** — через клиент `shared/api/todoistClient.ts` (единая точка конфигурации `@doist/todoist-sdk`: токен, обработка ошибок авторизации)
- **expo-sqlite** — через репозиторий `shared/api/widgetsDb.ts` (конфигурация фильтров виджетов)

Компонент из `ui/` не обращается ни к `fetch`, ни к `expo-sqlite` напрямую — только через хук/функцию из `api/` своего слайса. Другие стандартные FSD-сегменты (`lib/`, `config/`) добавляются по тому же принципу — когда для них появляется код, а не заранее «про запас».

Наружу слайс отдаёт **публичный API** — barrel-файл `index.ts`, реэкспортирующий только то, что нужно снаружи:

```ts
// features/create-widget/index.ts
export { CreateWidgetForm } from "./ui/CreateWidgetForm";
```

Импорт мимо `index.ts` в чужой слайс — нарушение границы слоя. Дублирование компонентов и логики решается декомпозицией и рефакторингом, а не копипастой (**DRY**).

Слой `shared` не делится на именованные слайсы — его сегменты (`api/`, `model/`, `ui/`, ...) лежат прямо в корне слоя и каждый сам выступает единицей с собственным barrel-файлом `index.ts`, отдающим публичный API сегмента:

```ts
// shared/model/index.ts
export { SessionProvider, useSession } from "./SessionContext";
```


## Naming и структура компонента

- Компоненты — `PascalCase.tsx`, один компонент на файл, имя файла = имя компонента
- Типизация функционального компонента — через `FC` из `react`:
  ```ts
  export const WidgetCard: FC<WidgetCardProps> = ({ widget }) => {...};
  export const ThemeProvider: FC<PropsWithChildren> = ({ children }) => {...};
  ```
- Пропсы компонента и любые другие типы — через `type`, не `interface`. В проекте нет классов с `implements`, для которых `interface` был бы оправдан, поэтому `interface` не используется вовсе:
  ```ts
  type WidgetCardProps = {
    widget: Widget;
    onPress: () => void;
  };
  ```
- Избегай inline-типов: максимум 2 поля для inline-типа, если больше — выноси в отдельный тип
- Экспорты — именованные (`export const X`), не `default`; наружу слайса — через `index.ts`
- `api/*.ts` — функции, обращающиеся к `todoistClient`/`widgetsDb`, и хуки TanStack Query/Mutation, построенные поверх этих вызовов (`useWidgetsQuery`, `useCreateWidgetMutation`). **Один файл — одна функция/хук, имя файла = имя экспорта**, а не общий `widgets.ts`/`tasks.ts` на весь сегмент:
  ```ts
  // api/fetchTasksByFilter.ts
  export const fetchTasksByFilter = (filterQuery: string): Promise<Task[]> =>
    todoistClient.getTasksByFilter({ query: filterQuery });

  // api/useWidgetsQuery.ts
  export const useWidgetsQuery = () => useQuery({ queryKey: widgetsListQueryKey, queryFn: getAllWidgets });
  ```
- `model/*.ts` — не-UI логика сегмента: Zod-схемы, локальное состояние, вычисления
- Относительный импорт (`./`, `../`) — только между сегментами (`ui/`, `model/`, `api/`) **одного и того же слайса** (например, внутри `features/login/*`). Импорт между разными слайсами, разными сегментами `shared` (у него нет слайсов — `shared/api` и `shared/model` для друг друга такие же чужие единицы, как разные слайсы) или разными слоями — строго через алиас (`@/app`, `@/pages`, `@/widgets`, `@/features`, `@/entities`, `@/shared`), даже если по факту до файла можно дотянуться через `../`


## Язык кода

Весь код — на английском, уровня **B2**: имена переменных/функций/компонентов, комментарии, JSDoc, сообщения об ошибках, тексты в тестах, ключи и служебные строки.

Комментарии пишутся только для логики, которая **не очевидна с первого взгляда** — скрытое ограничение, обход конкретного бага платформы, неочевидный инвариант. Комментарий, который пересказывает то, что уже понятно из именования, не пишется. Комментировать каждую строку/блок подряд не нужно.

Русский язык — только в документации (`docs/`, `README.md`, `CLAUDE.md`). Русские формулировки из [`SPECIFICATION.md`](SPECIFICATION.md) задают **смысл** элемента, а не строку для вставки в код, — переводи их при реализации.


## Язык UI

Строго английский — интерфейс приложения на английском языке независимо от локали устройства (см. [`SPECIFICATION.md`](SPECIFICATION.md)). Отдельного словаря локализации в проекте нет, пользовательские тексты живут прямо в JSX-компонентах.


## Роутинг (Expo Router)

Файловая маршрутизация — `src/app/`: каждый файл там (кроме `_layout.tsx`) — экран, каждая `_layout.tsx` — layout-роут для своей директории.

- `src/app/_layout.tsx` — корневой layout, точка инициализации `QueryProvider` и других провайдеров из `app/` (замена `App.jsx` из немаршрутизируемых RN-проектов)
- Нероутинговый код (компоненты, хуки, утилиты, модель) в `src/app/` не кладётся — только сами роуты и `_layout`-файлы; вся бизнес-логика живёт в слоях FSD и импортируется в роут через алиасы
- **Группы** — директория в круглых скобках (`(auth)`, `(app)`) не влияет на итоговый URL/deeplink, но позволяет разделить неавторизованную и авторизованную части приложения на уровне файловой структуры, не задавая это через собственную проверку токена на каждом экране
- Состояние авторизации, которое решает, какая группа роутов активна, — из `useSession()` (`app/SessionContext.tsx`), а не проверка токена в отдельных роутах
- Динамические роуты (`[id].tsx`) — только там, где экран параметризован сущностью (например, форма редактирования конкретного **Виджета**); параметры читаются через `useLocalSearchParams` из `expo-router`
- Импорт `Link`, `router`, `useLocalSearchParams` — только из `expo-router`, не из `react-navigation` напрямую


## TanStack Query — лучшие практики

- Запрос к Todoist API (через Todoist SDK) или к `expo-sqlite` — функция в `api/` слайса, оборачивается в `useQuery`/`useMutation` там же (не в компоненте `ui/`); `useState` остаётся для чисто локального UI-состояния (открыт ли модал, выбранный таб), не для серверных/персистентных данных
- **Query-ключи — иерархические массивы**, а не плоские строки: `["widgets", "list"]`, `["tasks", "list", { widgetId }]`. Порядок элементов массива значим (разные последовательности — разные кэши), порядок полей объекта — нет
- Query key, которым делятся несколько слайсов, заводится в `entities/` и импортируется оттуда — не дублируется:
  ```ts
  // entities/widget/model/queryKeys.ts
  export const widgetsListQueryKey = ["widgets", "list"] as const;
  export const widgetTasksQueryKey = (widgetId: string) =>
    ["tasks", "list", "widget", widgetId] as const;
  ```
- `staleTime` всех запросов к Todoist — общая константа `STALE_TIME` из `shared/api/queryConfig.ts`, а не повторяемое магическое число в каждом хуке
- **Мутация, меняющая состояние виджета или задачи, обязана инвалидировать все связанные кэши списков, а не только тот, из которого была вызвана** (одна и та же **Задача** видна и в превью виджета, и в его полном списке). После успешного результата мутации — `queryClient.invalidateQueries` по общему префиксу ключа:
  ```ts
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: widgetsListQueryKey, refetchType: "none" });
  }
  ```
  **Всегда указывай `refetchType: "none"`.** Без него `invalidateQueries` форсирует немедленный рефетч всех активных query из-под префикса — в том числе экрана, на котором пользователь только что сделал оптимистичное изменение, что превращается в гонку между оптимистичным состоянием и ответом форсированного рефетча. `refetchType: "none"` помечает кэши невалидными без сетевого запроса; свежие данные будут получены при следующем маунте
- Оптимистичные обновления (`onMutate`/`setQueryData`, откат в `onError`) — стандартный способ применять мгновенные UI-изменения при создании/редактировании/удалении **Виджета**, даже если запись идёт в локальную SQLite, а не на сервер, — отклик интерфейса не должен ждать завершения записи в БД
- Кэширования сверх того, что даёт TanStack Query по умолчанию, не делай без явного запроса


## React Hook Form + Zod — лучшие практики

- Схема Zod в `model/` слайса — единственный источник и валидации, и типа: тип формы выводится через `z.infer<typeof schema>`, а не описывается вторым независимым `type`
- Валидация подключается через `zodResolver` из `@hookform/resolvers/zod`:
  ```ts
  // model/widgetFormSchema.ts
  export const widgetFormSchema = z.object({
    name: z.string().min(1),
    query: z.string().min(1),
  });
  export type WidgetFormValues = z.infer<typeof widgetFormSchema>;

  // ui/WidgetForm.tsx
  const form = useForm<WidgetFormValues>({
    resolver: zodResolver(widgetFormSchema),
  });
  ```
- Если значения формы требуют трансформации (например, строка даты → объект `Dayjs`), различай `z.input`/`z.output` схемы вместо ручного приведения типов на стороне компонента
- Ошибки поля — через `form.formState.errors`, показанные рядом с полем; самодельная логика валидации в обработчике `onSubmit` не пишется, если её можно выразить в Zod-схеме
- Схема конфигурации **Виджета** (`widgetFormSchema`) переиспользуется и при записи в `expo-sqlite`, и при форме редактирования — не дублируется вторым описанием полей


## day.js

- Импорт и конфигурация плагинов — одна точка входа `shared/lib/date.ts`, остальной код импортирует `dayjs` только оттуда, не из пакета напрямую
- `moment` в проект не добавляется — day.js уже покрывает форматирование и сравнение due-дат задач


## Оптимизация и мемоизация

В проекте включён **React Compiler** (`experiments.reactCompiler: true` в `app.json`) — он на этапе сборки анализирует компоненты и хуки (функции с большой буквы или префиксом `use`) и сам расставляет эквивалент `useMemo`/`useCallback`/`React.memo`, если код соблюдает **Rules of React**: рендер должен быть чистым — без мутации пропсов/состояния и без побочных эффектов во время рендера.

- **Не расставляй `useMemo`/`useCallback`/`React.memo` вручную «про запас»** — это дублирует то, что уже делает компилятор, добавляет шум и увеличивает риск забытой/неверной зависимости. Пиши простой код без ручной мемоизации по умолчанию
- Компилятор ничего не даёт, если **Rules of React** нарушены — не мутируй пропсы/состояние напрямую, не читай и не записывай внешние переменные во время рендера, держи рендер-функцию чистой
- Компилятор оптимизирует **только компоненты и хуки** — обычные функции-утилиты (`model/`, `shared/lib/`) он не трогает. Для дорогого вычисления, вызываемого из обычной (не-хук) функции, кэшируй результат явно на её уровне, а не полагайся на автоматику
- Компилятор не управляет зависимостями `useEffect`/`useLayoutEffect` — их состав по-прежнему проверяй руками: только то, что реально используется внутри эффекта, и ничего лишнего
- Для больших списков (`FlatList`/список внутри `ListWidget`) — тюнинг виртуализации остаётся ручным и не относится к задаче компилятора: стабильный `keyExtractor`, при необходимости `initialNumToRender`/`maxToRenderPerBatch`/`windowSize`, `renderItem` не пересоздаётся инлайн-функцией на каждый рендер списка
- Виджеты `react-native-android-widget` (`FlexWidget`/`ListWidget`) рендерятся вне обычного React-дерева приложения — в отдельный снапшот для Android, не под наблюдением React Compiler рантайма приложения. Дерево виджета держи неглубоким, а тяжёлые вычисления (фильтрация/сортировка задач) делай до передачи данных в виджет, в `api/`/`model/` слайса, а не в самом рендере виджета
- Если после всего этого конкретный экран всё равно тормозит — сначала профилируй (React DevTools Profiler / замеры), находи, что именно медленно, и только потом добавляй точечную ручную оптимизацию именно там — не по всему компоненту


## Рецепт: как добавить функциональность

Порядок шагов — снизу вверх по слоям FSD: сначала то, что переиспользуется, потом композиция.

### Новая фича или экран

1. Определи слой по смыслу: бизнес-сущность → `entities`, одно пользовательское действие → `features`, крупный самостоятельный блок из нескольких фич → `widgets`, экран под route → `pages`
2. Заведи слайс `<layer>/<name>/` с сегментами `ui/`, `model/` и `api/` — только теми, для которых реально есть код
3. `api/` — обёртки над `todoistClient`/`expo-sqlite` и хуки TanStack Query/Mutation поверх них; `model/` — Zod-схемы, локальное состояние, вычисления
4. `ui/` — компоненты, один на файл, `FC`, декомпозиция до отдельной логической/визуальной единицы. **Каждый самостоятельный компонент — в отдельный файл**: если внутри JSX выделяется кусок разметки со своей логической ответственностью (карточка в списке, строка формы, элемент внутри `renderItem`), он выносится в собственный `PascalCase.tsx` рядом, а не остаётся вложенной функцией/JSX-фрагментом внутри родителя
5. `index.ts` — публичный API слайса: реэкспорт только того, что нужно снаружи
6. Подключи слайс сверху: в страницу, виджет или роутер (см. «Роутинг»)
7. Тест рядом с компонентом на пользовательские сценарии (см. «Тестирование»)

### Правка существующего компонента

Если компонент разросся или логика повторяется — выдели подкомпонент или функцию в `model/`, а не копируй. Три похожих случая — повод для общего компонента в `shared/ui`, два — ещё нет.


## Чего делать нельзя

- Обращаться к `fetch`/`todoistClient`/`expo-sqlite` напрямую из `ui/` или `model/` — только через функцию `api/`-сегмента
- Импортировать из чужого слайса мимо его `index.ts` или из слоя выше по списку (`entities` не знает про `features`, `features` — про `widgets` и `pages`)
- Дублировать Zod-схему или тип, уже определённый в `entities/`
- Создавать пустые слои и сегменты впрок
- Использовать `interface` для пропсов компонента или любых других типов — только `type`
- Класть нероутинговый код в `src/app/`
- Инвалидировать кэш мутацией без `refetchType: "none"`
- Оборачивать компонент/значение в `React.memo`/`useMemo`/`useCallback` без измеренной проблемы производительности — доверяй React Compiler (см. «Оптимизация и мемоизация»)


## Тестирование

Обязательному покрытию unit-тестами подлежат UI-компоненты с функциональностью — формы и интерактивные виджеты, а также вынесенная из них логика (хелперы и кастомные хуки в `model/`/`lib/`). Чисто презентационные компоненты без ветвлений и обработчиков тестами можно не покрывать.

- Тест — `*.spec.tsx` (`*.spec.ts` для хелперов/хуков без JSX), лежит рядом с тестируемым файлом
- **Один компонент/хелпер/хук — один файл тестов.** Файлы тестов не дробятся на несколько ради отдельных сценариев — деление на логические блоки внутри файла через `describe`/`it`, а не через новые файлы
- Рендеринг и запросы к дереву — `render`, `fireEvent`, `waitFor`, `screen` из `@testing-library/react-native`
- Запросы к дереву — через доступные пользователю признаки (`getByRole`, `getByText`, `getByLabelText`), не через `testID`, кроме случаев, где у элемента нет доступной пользователю роли или текста
- Todoist SDK и `expo-sqlite` в тестах мокаются на уровне функций `api/`-сегмента, а не на уровне `fetch`/нативного модуля
- Сценарий, взаимодействующий с формой на `react-hook-form` (сабмит, смена значения поля), в текущей версии `@testing-library/react-native` ломает следующий `render()` в том же файле (падает с ошибкой рендера тестового дерева) — несколько таких сценариев для одного компонента выражай **одним** `it`, последовательно меняя значение поля и сабмитя заново, а не отдельными `it`, каждый со своим `render()`


## SDLC

1. Разработка новой фичи / внесение правок
2. Добавление / актуализация unit-тестов
3. Проверь, нет ли висящих ссылок, нужно ли обновить документацию (`docs/README.md`, `CLAUDE.md`) — по «Правилу актуализации» из [`CLAUDE.md`](../CLAUDE.md)
4. `bunx tsc --noEmit` и `bunx biome check --write .`
5. `bunx jest`
6. Ожидание ревью от человека
7. `/git-commit`

При изменении зависимостей — дополнительно `npx expo-doctor` перед шагом 4.
